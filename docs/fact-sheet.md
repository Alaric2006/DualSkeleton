## C. 手势判定与和弦推导（目标站原始实现）

- **C1** `[确证][原站实现]` 手指伸展判定为 **尖端 y < PIP y**（图像坐标 y 向下）。该写法依赖手的朝向，仅记录为原站做法。
  - 注：本项目改用关节夹角，属**新增扩展**，不是逆向结论。
- **C2** `[确证]` 拇指「按下」判定：右手 `lm[4].x > lm[3].x`；左手 `lm[4].x < lm[3].x`。
- **C3** `[确证]` 大/小调判定：`lm[9].x > lm[0].x ? "minor" : "major"`。
- **C4** `[确证]` 左手级数：数「拇指按下 + 四指伸展」这五个布尔的个数得 1–5 对应 I–V；食指+小指（拇指未按）为 VI；食指+小指+拇指为 VII。
- **C5** `[确证]` 右手和弦性质：数 `[食指,中指,无名指,小指]` 的伸展个数得 0–4。
- **C6** `[确证]` 半音升降：取所有关键点 y 的最大值，`< 0.5` 为 raise，`>= 0.8` 为 lower，其余为 off；需对应开关打开才生效。
- **C7** `[确证]` 手部倾斜（弯音）：以腕部 x 为基准，比较 `lm[9]` 与 `lm[13]` 的 x 区间，超出阈值 0.12 后归一化并 clamp 到 ±1；右手取反。
- **C8** `[确证]` 时序稳定：手势需保持 **100 ms** 才提交；手消失 **50 ms** 内沿用上一结果。
- **C9** `[确证]` 调式表：12 个调 × 7 个音级，例如 `C:[C,D,E,F,G,A,B]`、`Gb:[Gb,Ab,Bb,Cb,Db,Eb,F]`。
- **C10** `[确证]` 音级到半音偏移：`{1:0, 2:2, 3:4, 4:5, 5:7, 6:9, 7:-1}`（七级回落到下方八度）。
- **C11** `[确证]` 和弦拼装：大三和弦为 根/三/五 + 高八度根/三；七和弦按性质取 maj7(+11)、dom7(+10)、dim7(+9)、dim5(+6)；命名 `Root / 1st / Maj 7 / Dom 7`（大调）与 `Root / 1st / Min 7 / Dim 7`（小调）。

### D6 性能降级策略

- 初始 stride = 3。
- 依据（阶段 0 基准实测，300 帧、30 帧预热、双手与人体检测率均 100%）：
  - p50：手部 16.8 ms / 姿态 8.6 ms / 串行合计 24.7 ms；
  - p95：手部 34.2 ms / 姿态 17.3 ms / 串行合计 49.8 ms；
  - 合计 ≈ 两者之和，说明同线程串行、无跨模型争抢，代价线性叠加。
  - 按 `16.8 + 8.6/N` 估算：
    - N=2 → p50 平均 21.1 ms（+25.6%，超 20% 上限）；
    - N=3 → p50 平均 19.7 ms（+17.0%）；p95 平均 39.9 ms（+16.7%）。
  - p50 与 p95 两个口径均在手部降幅 20% 以内，故初始 stride=3。
- 自适应判定只看「手部推理耗时的滚动 p50」，不看整体 fps：
  - > 20 ms 持续 1 s → stride +1（3→4→6）
  - < 14 ms 持续 3 s → stride −1（6→4→3），下限 3，不回落 2
  - 仅当手部 p50 < 12 ms 且整体 fps > 50 持续 3 s → 才允许 stride=2
  - 理由：画面中「有人无手」时手部只需约 4.4 ms（仅掌部检测），用整体 fps 当余量指标会误判为有余量而降 stride，手一入画立刻掉帧。
- stride=6 仍不足 20 fps → 停止姿态推理、保手部，面板与控制台明确告警。
- 基准环境为 headless 软件 GL，绝对值偏悲观；阶段 3 真机摄像头复测后回填绝对值，比例结论不变。

#### 基准条件（可复现）

- 环境：Windows，Chrome 155 headless，1280×720。
- 输入：同一帧图像 `male_full_height_hands.jpg`（MediaPipe 官方素材）绘到 canvas，`captureStream(30)` 供 `detectForVideo` 读取；手部与姿态检测率均为 100%。
- 参数：HandLandmarker（GPU / VIDEO / numHands 2）、PoseLandmarker lite（GPU / VIDEO / numPoses 1 / outputSegmentationMasks false）。
- 采样：30 帧预热后连续 300 帧；每帧先 hand 后 pose，共用同一时间戳；不渲染 UI、不做平滑。
- 计时：`performance.now()` 包住两次同步调用；单帧耗时 = hand 耗时 + pose 耗时。
- 仅测推理，不含视频上传、绘制与面板刷新，不能直接当作页面 fps。

#### 真机实测记录（2026-10-22）

- 环境：用户实机，硬件 GPU（非 headless 软件渲染）。
- 现象：双模型并行推理未触达性能瓶颈；rVFC 主循环稳定运行在 30fps 垂直同步上限；关闭姿态推理后 fps 无变化，说明单帧耗时远低于 33ms 预算。
- 结论：D6 的 stride 自适应策略在低端设备 / 软件渲染下兜底有效；在高端设备下维持初始 stride=3 即可满帧运行。原有比例估算结论不变。
